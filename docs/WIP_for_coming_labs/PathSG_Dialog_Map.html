PathSG Dialog Map

Every screen, sub-state, dialog and transition in the PathSG interface, drawn as UML state machine diagrams -- one per feature area. Each state is something the user sees; each transition is labelled trigger [guard] / effect, and traceability to the use cases and requirements is carried in attached UML notes.

UC IDs refer to the Use Case Descriptions (v1.4); REQ IDs to the functional requirements of the SRS (v1.4); PERF / SEC / QUAL / BR IDs to the non-functional requirements and business rules. This version describes the application as shipped. Screen names and routes are those of the client router (client/src/router/index.ts).

Changes from the Lab 3 version (v1.0, based on Use Case Descriptions v1.0)
  • Home screen (/) (SRS section 4.7, REQ-7.1 and REQ-7.2) is now where a visit starts, not the Directory. The "Where are you now?" route leads to the Directory or to the Roadmap.
  • Logout ends at the Directory; a refused token renewal ends the session with a banner; the login limit (5 per 5 minutes) is shown as a rejected login.
  • Directory: course filter (Post-Secondary and University), distance filter with its postal-code hints, keyword sanitising, load-failure and empty-tier states, the school location map.
  • Roadmap: ranking priority (Rank by Grade or Distance), distance slider (re-ranks on release), About dialog, no Rule-Based Plan for Preschool and University, a map in every plan panel, the AI timeout of 15 s (was 5 s) and rate limit, and an own Retry for the Rule-Based Plan.
  • Admin: several CSV files per update, update limit of 10 s (was 5 s), the "update already running" refusal, and the new Export Database flow (UC-5.2).
  • Errors: dialogs are used for confirmations (overwrite, delete roadmap, delete review), the missing-postal and guest-review prompts, and failed admin updates and exports. Every other failure is an inline message or a banner, as drawn.

1School Directory and profile

Search, filter and sort are internal transitions of one state, so the alternative flows (no match, malformed keyword, load failure) resolve through states and guards rather than separate pages. Selecting a card is the only transition that leaves the directory; back returns to the same tier, criteria, sort order and page, because the directory remembers them. The bookmark control exists only for signed-in users.

PathSG: Dialog Map -- UML state machine notationUse Case Descriptions v1.4 · SRS v1.4 · page 4 of 9

2Account and student profile

Log in and Create account are two tabs of one state, so both paths reach the same session. The profile is the data spine of the system: its postal code anchors every distance and its target level pre-selects the roadmap stage, and neither can be stored out of range. Rejected input stays on the form; only a valid, accepted submission moves on.

PathSG: Dialog Map -- UML state machine notationUse Case Descriptions v1.4 · SRS v1.4 · page 5 of 9

3aRoadmap generation

Generation is modelled as a composite state with two orthogonal regions, because that is the guarantee the requirements ask for: the rule-based region completes on its own clock, and any fault in the AI region stays inside that region with a retry of its own. Moving the ranking controls re-ranks only the rule-based region. Saving continues in map 3b.

PathSG: Dialog Map -- UML state machine notationUse Case Descriptions v1.4 · SRS v1.4 · page 6 of 9

3bSaving, editing and deleting a roadmap

One roadmap may be stored per account, which makes the overwrite confirmation part of the ordinary save path rather than an edge case. Cancelling anywhere leaves the stored record untouched. Plans on screen hide the saved roadmap without deleting it.

4School reviews

The submachine referenced by the school profile. Its first choice reads the session and the account's review history, so the same section opens gated, as a composer, or as the author's own card; editing and deleting are reachable only from that card.

PathSG: Dialog Map -- UML state machine notationUse Case Descriptions v1.4 · SRS v1.4 · page 8 of 9

5Admin: school dataset update and export

One panel, two independent triggers. Update locks its own controls for the run, and both failure branches leave the database as it was, so the panel always returns to a truthful idle state showing the last successful update. Export never touches the update lock.
