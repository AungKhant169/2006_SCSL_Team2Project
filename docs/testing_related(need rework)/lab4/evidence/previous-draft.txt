Our prompt

Examine the existing code within our code base and provide clear and constructive feedback regarding its quality. Ensure that the feedback is objective and well-reasoned. Next, provide suggestion as to what can be further refactored.

AI’s Response

Code Review: PathSG

Overall this is a well-organised codebase with clear conventions, strong test discipline, and requirement traceability (REQ-/UC-/BR- tags). Below are findings by area, followed by refactoring suggestions in priority order.

Strengths

Client architecture

Clean layering: views/ → components/ → stores/ → services/ → utils/. Pure logic (schoolSearch, benchmark, profileValidation, roadmapPlan) is separated from Vue and is easy to test.

Design tokens in theme.css plus @layer components modules, wrapped by BaseButton, FormField, SectionCard etc. This keeps class lists from being repeated.

Good accessibility habits: useId label wiring in FormField, aria-pressed on toggles, role="alert", focus management in ModalDialog, and 44px touch targets in the mobile menu.

Race-condition handling in roadmap.ts (aiRun counter) is correct and tested for both the resolve and reject paths.

http.ts and authService.restoreSession handle failure modes carefully, including the distinction between “server unreachable” and “session rejected”.

Test quality is high: boundary-value analysis in profileValidation.spec.ts, whole-app journeys in App.spec.ts, and shared helpers (mountWithApp, stubAuthApi).

Server

The HttpError enum pattern with (status, detail) tuples is compact, and tests reverse-map responses back to enum members.

Model-level @validates hooks keep invariants close to the data (roadmap choices, username/password patterns).

The AI generator uses a strict JSON schema, filters returned ids against the valid pool, and deliberately withholds the username from the prompt. _parse_choices is defensive.

The multi-stage Dockerfiles, .dockerignore files and the single-worker comment (refresh tokens are in memory) show operational awareness.

Suggested Refactors (in priority order)

Introduce an API layer on the client and retire the seed data. Add schoolService.ts and roadmapService.ts mirroring authService.ts. Replace data/schools.ts consumers (searchSchools, getSchool, roadmapPlan, bookmarks) with a useSchoolsStore that fetches and caches. Decide on one identifier (school_key is the stable choice) and use it in routes, bookmarks and roadmap choices.

Add roles and authorisation on the server. Add role to User (with a migration), expose it in Identity, add an AdminRequester dependency, and have the client’s isAdmin read from it.

Make persistence atomic. Give Persistable a session() context manager and add upsert. Rewrite Roadmap.save as one transaction and handle IntegrityError.

Move refresh tokens into the database (hashed, with expiry and rotation), and consider HttpOnly cookies for the refresh token. This also removes the single-worker constraint.

Harden auth endpoints. Use a single generic login failure message, add rate limiting (e.g. slowapi), and add an upper bound on request body size.

Extract a shared roadmap domain module on the server. Define Stage, Source, PLAN_LENGTH once, split roadmap_rules.py into per-stage strategy classes behind a small protocol, and add unit tests for each strategy and for Geolocation.

Replace ilike('%level%') with explicit level mappings in candidate_pool and SchoolInfo.search, and escape LIKE wildcards in q.

Decouple stores. Add a resettable Pinia plugin so logout calls one resetAll(), and move DEFAULT_POSTAL to a constants module. Split ui into notice and modal composables.

Type tightening. Make BaseSelect generic, introduce branded or literal types for school ids once the API lands, and generate client types from the FastAPI OpenAPI schema (e.g. openapi-typescript) so the contract cannot drift.

CI and hygiene. Run vitest, vue-tsc, ruff check and pytest in CI (the Dockerfile references .github/workflows/ci.yml). Add server coverage reporting, remove dead debug code, fix the misleading comments listed above, and update the README to reflect which areas are real versus simulated.

If useful, I can draft any of these (for example the Persistable transaction refactor, the role migration, or the client schoolService and store) as concrete diffs.
